The headline — agentic AI

Reasoning layer · Gemini function-calling · Python / Vertex AI

An orchestrator with agents that reason for themselves

Not a prompt-and-pray script. ARIA is a set of autonomous agents that decide what to read, read it through a live tool layer, and reason their way to a structured, defensible plan — designed to grow into a whole copilot, not a one-off feature.

  • A1

    Designed a multi-agent architecture, from scratch

    Architected ARIA as an orchestrator + peer sub-agents — Today's Plan, Client Intelligence, and an AI Pre-Brief playbook — each a Gemini function-calling tool-loop that autonomously sequences its own work: read the calendar, pull the client pipeline, deep-read each candidate, fetch a transcript only when it needs one, then rank and sequence the day. Built the orchestrator to add new agents (plan-reco, docs, email) with no new plumbing.

Encoded the day-planning judgment (working-hours, overlaps, gap-filling, priorities) as explicit prompt rules I iterated against real production traces, watching live plans and tightening the reasoning until they were right.

What "agentic" actually means here

One agent, thinking in a loop

Each agent runs a Gemini tool-loop: it chooses the next tool based on what it has learned so far, calls it over gRPC, absorbs the result, and repeats — until it has enough to commit a plan. The reasoning is the agent's; the data is always live.

And I owned the whole stack around it

The agent is the star — but I built everything it stands on

An agent is only as good as the system feeding and surfacing it. I designed and shipped both ends myself: the backend that owns the data and serves the agent's tools, and the realtime frontend contracts that put the plan on the agent's screen.

Backend The data & tool layer

Kotlin / Spring · gRPC · PostgreSQL

  • Designed a stateless split — the AI service reasons and never touches the database; the backend owns all CRM & calendar data and exposes a scoped gRPC tool API the agents call. A clean, safe boundary that let AI features ship without ever risking the source of truth.
  • Built the tools the agents actually use: availability, client pipeline, per-client detail, transcripts, calendar writes, and the exact-match appointment resolver — each one scoped so an agent can only see one agent's data.
  • Ran an async, prioritized generation pipeline so a person waiting on-screen is always served ahead of the overnight bulk run — the interactive path never waits behind a batch.

Frontend The realtime surface

GraphQL (code-first) · WebSocket subscriptions

  • Defined a live WebSocket surface that streams the plan to the screen the instant it changes — sectioned and bounded so even a 1,500-client agent renders instantly instead of choking on a huge payload.
  • Shipped a sync-or-wait contract for the on-demand AI Pre-Brief: instant if it's cached, otherwise one round-trip that waits out generation — with the brief modeled as a self-describing blob so the AI can add fields with no schema change or frontend release.
  • Authored the integration contracts and field specs the client team built against — role-gated manager views, resilient type handling, documented shapes — so AI output rendered cleanly on day one.

Before any code

It started with the user, not the model

I ran the requirements-gathering and wrote the design docs that everything else followed — interviewing on how agents actually run their day, pinning down the sharp product questions (what counts as a "reconnect"? how do daily goal-rings reset across timezones and PTO?), and locking a principle set the whole build held to.

Discovery Turned a vague ask into a spec

user interviews · product questions · design docs

  • Translated "an AI command center for our agents" into a concrete three-surface product (Dashboard, Today's Plan, Next Actions) with a written vision, phased plan, and explicit open questions for design & product.
  • Grounded every decision in how the work is really done — appointments and blocks are fixed anchors; promised follow-ups, new leads, and high-intent clients get AI-sequenced around them.

Principles Decisions that held for months

architecture calls · locked constraints

  • Locked the calls that kept the system coherent: AI is the brain, the backend owns the data; calendar writes are propose → confirm, never unsolicited; deterministic CRM queries stay out of the LLM.
  • Chose an orchestrator from day one over a single-purpose planner — a deliberate bet that this becomes a growing copilot, so the second and third agents dropped in without a rewrite.

What this becomes

One copilot for the whole system — a hierarchy of agents that reason, loop, and fix

Today's Plan was the first agent. The architecture underneath it is built for many: an orchestrator that routes to specialist agents, each of which can spawn its own sub-agents — a tree of intelligence where every node reasons, calls tools, checks its own work, and retries until it's right. Not one model answering a prompt; a system of agents working together.

→Many agents, same spine

Every new capability — plan reco, documents, email, anything — drops in as a peer or sub-agent on the existing orchestrator and tool layer. No new plumbing.

→Agents that fix themselves

The reason-loop-verify pattern generalizes: agents that critique their own output, re-plan on failure, and escalate to a peer when stuck.

→Ask ARIA anything

Swap deterministic routing for an LLM router and the same agent tree serves free-text requests across the whole product — the nodes are already shaped for it.
