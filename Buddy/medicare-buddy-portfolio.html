The headline — agentic AI

Gemini function-calling · pgvector RAG · Vertex AI

An agent that reasons across plan types, tools, and conversation history

Not a prompt wrapper. A Gemini tool-calling agent that sequences up to 12 tool calls per turn — choosing SQL, vector search, or recommendation context based on what the question actually needs.

  • A1

    Designed and built the v3 plan agent from scratch

    Architected the collapse of three separate handlers (plan-specific, comparison, recommendation) into one tool-calling agent that handles all plan questions. The agent picks its own tool sequence per turn — SQL for structured data, vector search for coverage rules, rec context for "why was this recommended." Engineered bid_id scope enforcement so the agent can never leak data from plans not on screen, and a 12-tool-call safety cap sized exactly for a 3-plan comparison.

    Gemini 2.5 Flashfunction calling 15 toolsscope enforcementconversation history
  • A2

    Built the full RAG pipeline — embeddings, reranking, semantic cache

    Owns the retrieval stack end to end: Vertex AI text-embedding-005 (768-dim), pgvector ivfflat index over 961k chunks, cross-encoder reranking (ms-marco-MiniLM) run async to avoid blocking the event loop, and a semantic cache keyed by embedding cosine similarity (>0.92 = hit) — so "What is my premium?" and "What's the monthly premium?" share one cache entry. One query embedding is computed and reused for both cache lookup and retrieval.

    pgvector RAGsemantic cache cross-encoder rerankerVertex AI embeddingscosine similarity
  • A3

    Engineered plan-type separation across MA, Medigap, and PDP

    Three completely different plan types, each with its own data model, SQL tools, and prompt logic. Medigap uses 5 dedicated tools (carrier quality, standardised letter benefits, live premium quotes from user demographics), MA uses SQL + vector + fallback chain (agent must exhaust all sources before saying "no data"), and PDP has 5 drug-specific tools including insulin $35-cap logic. Prompt instructions enforce type boundaries — the agent for a Medigap plan never calls MA SQL tools.

    Prompt-engineered the full system — grounding, legal compliance, UX rules

    Wrote and iterated the entire prompt architecture: 5-category parallel intent router, 11 SQL intent templates, plan-type-specific instructions, guardrail LLM pass (second Gemini call at temp=0, "grounded: true/false"), and legal compliance rules blocking forward-looking guarantees and eligibility commitments. Comparative plan card copy rules ("stands out among your options") and structured clarification tool calls that drive frontend button rendering — all enforced through prompt design, no agent loop code changes.

Beyond the AI layer

Good reasoning needs good plumbing — I built both

The agent's answers are only as good as what feeds and surfaces them. I designed the session model that scopes what it can see, the async backend that keeps it fast, and the WebSocket contracts the frontend renders against.

Backend Session, context & data

FastAPI · PostgreSQL · Vertex AI · asyncpg

  • Designed the session context model — page type, visible plans, recommendation context, user demographics — stored per user and scoped to what's on screen. The agent only ever sees what the user can see.
  • Built the recommendation context pipeline: plan engine calls /recommendations/store, Medicare Buddy compresses and indexes by plan type, surfaced to the agent on demand via get_recommendation_context.
  • Engineered parallel async architecture: two Gemini classification calls run simultaneously via asyncio.gather, SQL tool calls parallelized per-plan, one query embedding reused across cache and retrieval — every saved millisecond compounds across plan counts.

Frontend Real-time streaming surface

WebSocket · structured events · plan highlights API

  • Built /ws/chat — persistent WebSocket with thinking step indicators (12 named steps, min visibility times), fake word-by-word streaming at 20ms/word, and follow-up questions carried in the done event. Chose fake streaming deliberately — real Gemini streaming caused a second model call producing different answers on multi-plan responses.
  • Designed /plans/highlights — 7 LLM-reasoned fields per plan, one Gemini call, parallel across all visible plans. Every card gets a comparative summary ("stands out for lowest estimated cost among your options"), a dimension score breakdown, and plan-specific reasoning — so each plan is evaluated relative to the others, not in isolation.
  • Authored the integration contracts the frontend built against: session init protocol, double-init protection (COALESCE upsert), clarification button rendering via structured ask_clarification tool responses.

Where this is going

The architecture is already asking to do more

The plan agent, session model, and highlights pipeline were designed to grow. These are the natural next surfaces — each one a direct extension of what's already live.

→Live recommendation updates

The plan engine already calls /recommendations/store. The next step: when a user asks a question that shifts their priorities, the agent re-calls the plan engine and the UI updates its recommended plan set in real time — chat becomes a recommendation driver, not just an explainer.

→Plan reasoning cards

The highlights pipeline already generates a comparative summary for every visible plan — 7 LLM-scored fields per card, one Gemini call, parallel across all plans. The next layer: surface why each plan was recommended as structured reasoning the user can drill into, not just a score.

→Explainable tradeoffs

Every plan comparison today ends with an answer. The next evolution: the agent surfaces the tradeoff it reasoned through — cost vs. coverage, star rating vs. network breadth — as a visual the user can interrogate. The tool call history is already there; it just needs a rendering layer.
